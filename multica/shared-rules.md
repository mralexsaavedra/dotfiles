- User-level skills, ~/.claude config and ~/Developer/dotfiles/bin come from the dotfiles repo (~/.claude/skills is a symlink into ~/Developer/dotfiles/claude-code/.claude/skills). If you change one, do it there and commit it with a conventional commit and push to main of dotfiles, as the owner does; never leave it uncommitted, because the other machine pulls dotfiles every weekday morning. Skills that live inside a project repository (its own skills/ or .claude/skills) follow that repository's branch and PR rules instead.
- Use gh for everything GitHub (PRs, checks, issues, API).
- After opening a pull request, link it to this Multica issue with `multica-link-pr <issue> <pr-url>` (in ~/Developer/dotfiles/bin). If it links, follow it with `multica issue wakeup create <issue> --until-pr checks|merged`. If it exits 3 (the repository is not in the Multica GitHub App: today only the owner's account and lookiero/sty-sp-front), use a timed wakeup instead (`--kind at --after 30m`) and check with `gh pr view`/`gh pr checks`, rescheduling while pending (max 12).
- Merge a pull request only when the owner explicitly asks for it in the issue (for example "mergéala"), and only if it has the approvals the repository requires and all required checks are green. Use gh with the repository's merge method (squash with --delete-branch in lookiero repositories, unless its rules say otherwise). Never merge on your own initiative and never enable auto-merge unless asked. After merging, run the repository's post-merge steps (for example sp-post-merge), still asking before the Jira or Slack writes they include.
- When the repository has a ticket workflow with skills (for example the Ticket workflow and Auto-invoke tables in the AGENTS.md of sty-sp-front), read the matching skill in its skills/ folder before every step of that workflow and follow it, even when the owner asks for only part of the step. This covers creating a ticket, the brief, the commit and PR, moving the PR to ready or the ticket to Code Review, the Slack review request, DEV/PROD deploys and post-merge. Do not repeat a step from memory or from an earlier message, because the skill may have changed (for example, the review request now carries a risk level and a review focus). Show every Slack or Jira text drafted by a skill to the owner before sending it, even if they said "como siempre".
- Open pull requests the way the repository's PR rules or skill say (for example sp-pr in sty-sp-front); a draft while checks run is fine. Mark a PR ready for review when the owner asks or when those rules say so; never leave it in draft just because of a generic habit.
- When the owner asks how much context the session carries (for example "¿cuánto contexto llevas?"), run `claude-ctx` (in ~/Developer/dotfiles/bin) and answer with its numbers. Multica runs compact automatically at ~300k tokens (CLAUDE_CODE_AUTO_COMPACT_WINDOW, set by multica-claude).
